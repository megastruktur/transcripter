# LOGIC_DIAGRAM_SIMPLIFIED.md — как устроен Transcripter, по-простому

Этот документ объясняет то же самое, что и технический
[LOGIC_DIAGRAM.md](./LOGIC_DIAGRAM.md), но без программистского жаргона.
Для человека, который хочет понять, **что вообще происходит** с его
записями, а не как написан код.

Работает всё на одном примере: представь, что ты записываешь свои
настольные игры в D&D каждую неделю. Transcripter — твой личный
секретарь с картотекой.

---

## 1. Что это вообще такое

Transcripter состоит из двух частей:

- **Приложение на компьютере** — кнопка «записать». Оно только слушает
  микрофон (и звук компьютера, если хочешь) и отправляет файл на сервер.
- **Сервер** — отдельная машина (или тот же компьютер) в твоей домашней
  сети, где живёт вся «тяжёлая» работа: распознавание речи, умная
  модель для текстов, картотека.

```
  ┌──────────────────┐         ┌─────────────────────────────┐
  │  Твой компьютер  │         │  Сервер                     │
  │  ┌────────────┐  │  файл   │  ┌───────────────────────┐  │
  │  │ запись     │──┼────────►│  │ расшифровка           │  │
  │  │ (микрофон  │  │ по      │  │ → кто говорил         │  │
  │  │  + звук)   │  │ частям  │  │ → пересказ            │  │
  │  └────────────┘  │         │  │ → картотека (память)  │  │
  └──────────────────┘         │  └───────────┬───────────┘  │
                               │              ▼              │
                               │  готовое переезжает         │  │
                               │  НАСОВСЕМ в Obsidian        │  │
                               └─────────────────────────────┘
```

Все умные штуки происходят у тебя дома — ничего не уходит в чужие облака.

---

## 2. Путь записи: от микрофона до результата

### Шаг 1. Ты нажимаешь «записать»

Приложение сначала **проверяет**, что микрофон живой и доступ разрешён
(чтобы не получить час тишины). Потом пишет звук в файл на диск —
даже если приложение упадёт, записанное не пропадёт.

### Шаг 2. Файл отправляется на сервер — по частям

Большой файл не отправляется целиком. Он идёт **кусками по 8 мегабайт**,
как письмо, отправленное по страницам. Если Wi-Fi отвалился на 40-й
странице — при следующем запуске отправка продолжится **с 40-й
страницы**, а не сначала. В конце сервер сверяет «контрольную сумму»
файла — убеждается, что ни один кусок не потерялся и не исказился.

### Шаг 3. Сборка конвейера

Дальше сервер гоняет запись через **конвейер из шести станций**. Каждая
станция берёт результат предыдущей и добавляет своё. Если одна станция
сломалась — конвейер честно пишет «сломалась станция №3», а когда
починят, можно перезапустить **только её** (и всё, что ниже), не
перегоняя всё сначала.

```
запись
  │
  ▼
1. НАРЕЗКА      ─ большая запись режется на кусочки по 10 минут
  │
  ▼
2. РАСШИФРОВКА  ─ звук превращается в текст с таймкодами
  │
  ▼
3. ГОЛОСА       ─ определяется, КТО когда говорил (голос 1, голос 2…)
  │
  ▼
4. СКЛЕЙКА      ─ текст + голоса = диалог с подписями говорящих
  │
  ▼
5. ПЕРЕСКАЗ     ─ умная модель пишет краткое содержание
  │
  ▼
6. КАРТОТЕКА    ─ из текста вытаскиваются «карточки» (события, люди, места)
  │
  ▼
готово: заметки и сам звук переезжают насовсем в Obsidian
```

### Станция 1. Зачем резать на кусочки?

Распознаватель речи иногда «застревает»: начинает повторять одну фразу
до конца файла. На двухчасовой записи это портило **всё** после места
сбоя. Поэтому запись режется на кусочки по 10 минут — застрял
распознаватель, испортился только один кусочек. Между кусочками
нахлёст в 2 секунды, чтобы ни одно слово не потерялось на стыке;
программа знает, какой половине нахлёста принадлежит каждая секунда,
и не напечатает её дважды. Резка нужна только расшифровке: станция
«Голоса» работает всегда с полной записью (см. Станции 3–4).

### Станция 2. Расшифровка

Программа слушает кусочки по очереди (не одновременно — сервер
один, иначе он задохнётся) и пишет текст с таймкодами:

```
[00:00:05 – 00:00:09] Гром достаёт меч и встаёт в дверях.
```

Если кусочек «застрял» (больше половины текста — одна и та же фраза),
он помечается подозрительным и при перезапуске расшифровывается заново,
со «сброшенной памятью» распознавателя.

### Станции 3–4. Кто говорил?

Голосовая станция слушает запись **целиком, одним куском** (не по
кусочкам, как расшифровка): модель DiariZen находит все голоса и
сопоставляет их между собой по всей записи сразу — поэтому «голос №1»
в начале и «голос №1» через два часа гарантированно один и тот же
человек. Она умеет и разговоры внахлёст, когда двое говорят
одновременно. Потом каждое слово текста получает того говорящего,
чей голос звучал в этот момент. Получается диалог:

> **Голос 1:** Гром достаёт меч.
> **Голос 2:** Я кастую огненный шар!

Эти станции — **необязательные**: если голоса не распознались или аудио
неудачное, запись не пропадёт — просто будет текст без подписей, кто
говорил.

### Станция 5. Пересказ

Текст отправляется в **языковую модель** — большую умную программу для
текстов (дальше буду звать её просто «модель»). Она пишет краткое
содержание: «Партия вошла в Тёмный замок, нашла артефакт, поссорилась
с лидером культа». Промпт (инструкция, как пересказывать) можно менять
под тип записи — отдельный для совещаний, отдельный для игр.

### Станция 6. Картотека — самое интересное

Модель просят прочитать текст и заполнить **карточки** трёх видов:

- **События**: «Гром достал меч», «партия вошла в замок»;
- **Сущности**: Гром (персонаж), Тёмный замок (место), артефакт (предмет);
- **Связи**: Гром — *владеет* — меч.

Карточки раскладываются по **ящикам**. Ящик — это **тег** записи.
Пометил запись тегом «dnd» — карточки пошли в ящик «dnd». Два тега —
копия карточек в каждый ящик. Нет тегов — есть ящик «без тега».

## 3. Дедупликация: «Это тот же Гром или другой?»

Самая хитрая часть. На следующей неделе модель снова услышит про Грома.
Нужно решить: это **тот же** Гром из прошлой сессии (тогда карточки
объединяем — Гром должен быть один, со списком всех сессий, где он
мелькал) или **другой** (тогда заводим вторую карточку: «Гром-2»).

Система решает в три этапа, от дешёвого к дорогому:

### Этап 1. По имени — бесплатно

Имена приводятся к единому виду: маленькие буквы, без лишних знаков.
«Гром», «гром» и «Гром!» — одно и то же. Совпало — проверяем дальше.
Не совпало — это точно разные карточки, дальше не смотрим.

### Этап 2. По «похожести смысла» — дёшево

Есть способ превратить слово в **набор чисел**, причём похожие по смыслу
слова дают похожие числа (это называется «эмбеддинг» — представь, что
каждое слово — точка на огромной карте, и смысловая близость = близость
точек). Система меряет, насколько два имени близки:

- близость **90% и выше** → одна карточка. Точка, вопрос закрыт;
- близость **75% и ниже** → разные карточки. Тоже точка;
- **между 75% и 90%** — «серая зона» → идём на этап 3.

Так большинство пар решается автоматически, не дёргая модель.

### Этап 3. Серая зона — спросить модель

Система спрашивает у модели буквально: «Гром из записи №5 и Гром из
записи №7 — один и тот же? Ответь: Да или Нет».

- **Да** → карточки сливаются;
- **Нет** → новая карточка «Гром-2»;
- **модель сломалась / ответила невнятно** → считаем «да». Нарочно:
  лучше случайно слить лишнее, чем плодить дубли в картотеке.

### Два сторожа

1. **Проверка перед расспросами.** Модель одна и очередь к ней общая.
   Если очередь перегружена, маленькие вопросы «да/нет» будут
   умирать по таймауту — и вся серая зона сольётся в «да» по ошибке.
   Поэтому перед пачкой вопросов система шлёт **один пробный вопрос**:
   ответил — работаем; нет — пропускаем расспросы, решаем только
   числами.
2. **Твои правки неприкосновенны.** Если ты **сам** переименовал
   карточку (скажем, модель расслышала «Валли», а ты исправил на
   «Валя»), на неё вешается флажок «исправлено человеком». Такую
   карточку:
   - никогда не сольют с другой автоматически;
   - никогда не перезапишут при повторной обработке записи;
   - не удалят при чистке.

## 4. Группировка: что с чем складывается

Коротко все «ящики» системы:

| Что объединяет | По какому признаку |
|---|---|
| Как пересказывать и какие карточки доставать | **тип записи** (совещание / игра — выбирает профиль-инструкцию) |
| В какой ящик картотеки класть | **теги** записи (каждый тег = отдельный ящик, копии в каждый) |
| Какие записи попадают в «память серии» | **тег** (дайджест — по последним N записям с этим тегом) |
| Кто говорил внутри записи | **голос** (станция 3) |
| Где это было в записи | **таймкод** |

Важно: ящики **полностью независимы**. Ящик «dnd» и ящик «совещания»
не знают друг о друге: в каждом свои карточки, свои слияния, своя
память.

## 5. Память: система помнит прошлые сессии

Вот замкнутый круг, ради которого всё и затевалось:

```
записи ──► карточки в ящике ──► дайджест ящика
   ▲                                │
   │                                ▼
   └──────── дайджест подкладывается в пересказ НОВОЙ записи
```

### Дайджест — заметка «о чём была серия»

По команде (или автоматически, когда заметка устарела) модель читает
карточки **последних N записей** ящика и пишет заметку: обзор,
повторяющиеся персонажи, хронику по сессиям, открытые вопросы. Она
лежит файлом `digests/dnd.md` рядом с остальными заметками.

### Как память помогает новому пересказу

Перед тем как пересказать **новую** запись, система подкладывает
модели в инструкцию:

1. **Дайджест ящика** — «вот что было в прошлых сессиях»;
2. **Похожие куски старых расшифровок** — система берёт начало новой
   записи (обычно там повестка) и ищет в картотеке абзацы старых
   записей, похожие по смыслу: «про Тёмный замок уже говорили в сессии
   3, вот цитата». Сама новая запись из поиска исключается — она не
   может быть «сама себе прошлым контекстом».

Поэтому пересказ седьмой сессии может написать: «партия **вернулась** в
Тёмный замок» — он знает, что они там уже были.

## 6. Поиск: «а когда мы обсуждали артефакт?»

Каждая запись при обработке нарезается на абзацы (по репликам, если
известны голоса, иначе скользящими окнами ~300 слов с перекрытием).
Каждый абзац превращается в набор чисел (та же «карта смыслов», что в
этапе 2 дедупликации) и складывается в файлик индекса своего ящика.

Поиск «артефакт» превращается в такие же числа и находит ближайшие
абзацы — даже если слова «артефакт» там нет, но говорилось «волшебная
штуковина из подземелья». Есть поиск внутри одного ящика и глобальный
по всем сразу (с подписью, из какого ящика каждая находка).

Если модель для чисел поменялась, старый индекс не подмешивается тихо:
система замечает несовпадение и либо перестраивает индекс, либо честно
говорит «индекс от другой модели, перестрой».

## 7. Obsidian: полка, на которую переезжает всё

Когда запись готова, её заметки — и **сам звук** — переезжают в твой
Obsidian-волт **насовсем**. Серверное хранилище теперь только рабочий
стол на время обработки: готовый результат живёт в волте. Записи
разложены по папкам-месяцам, у каждой записи своя папка:

```
2026/08/
  2026-08-30_21-00 Игра в замке a1b2c3d4/
    transcript.md            ← полный текст
    diarized-transcript.md   ← диалог с голосами
    summary.md               ← пересказ (имя может поменять профиль)
    .transcripter/           ← скрытая служебная папка: сам звук
                               и служебная копия всех материалов
```

Звук лежит в скрытой папке `.transcripter` — Obsidian её не показывает,
но если ты удалишь запись в приложении, она исчезнет и из волта.
В корне волта также лежит `Dashboard.md` — автоматически обновляемое
оглавление: список всех записей по месяцам и по тегам со ссылками.

Правила дома:

- **Переименовал запись** → переименовывается только папка. Файлы
  внутри **не трогаются** — твои ручные правки в заметках священны
  (заголовок внутри обновится при следующем пересчёте).
- **Пересчитал стадию** → файлы перезаписываются аккуратно: сначала
  новый файл рядом, потом мгновенная замена — ты никогда не увидишь
  «половину файла».
- Чего в папке не должно быть (например, диалога, если голоса
  отключили) — то убирается. **Твои собственные файлы** в папке не
  удаляются никогда.
- Дайджесты ящиков и поисковые индексы лежат в корне волта, в
  `digests/` и `indexes/`.

## 8. Правки и перезапуски

- **Поменял название** → переименуется папка в волте, больше ничего.
- **Поменял теги** → пересчитывается только картотека: карточки
  перекладываются в новые ящики, из старых убираются (за этим следит
  пометка «какая запись породила карточку»).
- **Поменял тип записи** → пересчитывается пересказ (новая инструкция)
  и за ним картотека.
- **Не понравилась одна стадия** → жмёшь «перезапустить станцию N» —
  пересчитается она и всё ниже по конвейеру.
- **Удалил запись** → из базы, с сервера и **из волта** (включая
  звук) удаляется сразу; карточки в картотеке подметает периодическая
  уборка (удаляет всё, чья запись больше не существует).

## 9. «А что если что-то сломается?»

Система построена на правиле «не усугубляй»:

| Что сломалось | Что произойдёт |
|---|---|
| Сломались голоса / картотека | Запись всё равно готова: текст и пересказ на месте. Эти станции — «постарались как могли» |
| Модель не отвечает при слиянии карточек | Считаем «та же карточка» и идём дальше |
| Очередь к модели перегружена | Расспросы отключаются заранее (пробный вопрос), решаем только числами |
| Упал NAS/диск с заметками | Выгрузка заметок умирает в отдельном коротком процессе и **бросается**, не вешая конвейер; потом есть команда догрузить всё разом. Пустое хранилище при загрузке — тревожный знак: выгрузка сама отказывается писать, пока не убедится, что диск на месте |
| Сервер перезагрузили посреди обработки | Конвейер продолжит с места остановки (статусы станций хранятся в базе; кусочки расшифровки — на диске) |
| Запись удалили | Периодическая уборка вычистит её следы из картотеки и индексов |

---

## 10. Одной фразой

**Запись → текст → кто говорил → пересказ → карточки по ящикам-тегам
(со слиянием дублей и неприкосновенностью твоих правок) → дайджест
ящика → дайджест помогает пересказать следующую запись → всё ищется по
смыслу → всё выгружается в Obsidian.**

Подробности с именами файлов, функций и порогов — в техническом
[LOGIC_DIAGRAM.md](./LOGIC_DIAGRAM.md).
