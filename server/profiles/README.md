# Profiles — контракт формата (host ≥ 0.10.0)

Профиль — это YAML-файл в этом каталоге: «если тип записи — X — суммируй
этим промптом и назови артефакт так-то». Профиль применяется, когда
`recording.type` записи равен `type` профиля. Профили перечитываются при
каждом запуске стадии — рестарт сервера НЕ нужен. Невалидный профиль
логируется (warn) и пропускается; сервер и остальные профили продолжают
работать.

## Формат

```yaml
id: my-profile                # обязательно; уникальный slug [a-z0-9-]
version: 1.0.0                # обязательно; semver версии ПРОФИЛЯ
min_host_version: 0.10.0      # обязательно; хост ниже — профиль пропускается (warn)
display_name: My Profile      # обязательно
description: Что делает профиль  # обязательно; кавычки, если есть двоеточие
type: meeting                 # обязательно; slug типа записи ([a-z0-9-]):
                              # профиль применяется, когда recording.type == type
summarize:
  prompt: |                   # обязательно; ОБЯЗАН содержать {transcript}
    Ты — … «{title}» …        # {title} — опционально
    {transcript}
  output_artifact: my-notes.md  # опционально; default summary.md;
                                # только [a-z0-9._-]
```

## Язык системных имён

Все СИСТЕМНЫЕ имена — только английские: значения `type`, `id` профилей,
`output_artifact`, типы и `kind` сущностей в enrich-секции, дефолтные
`node_labels`, имена артефактов. Контент (тексты промптов, саммари,
лейблы сущностей, свободные теги записей) — любой язык.

## Семантика

- **Матч**: `recording.type` записи равен `type` профиля → профиль
  применяется. Совпало несколько профилей (одинаковый `type`) → выигрывает
  первый по алфавиту `id` (в логе warn). У записи нет типа (NULL) или тип
  не матчит ни один профиль → встроенный summarize-промпт — поведение
  по умолчанию.
- **Промпт**: после подстановки `{title}`/`{transcript}` весь текст уходит
  одним user-сообщением в LLM суммаризации. Без профиля используется
  встроенный промпт — поведение прежнее.
- **Артефакт**: саммари всегда пишется в `meta/summary.md`; при экспорте в
  Obsidian-папку записи файл получает имя `output_artifact`.
- **Применение**: профиль матчится на момент запуска стадии. Смена `type`
  у существующей done-записи → хост сам перезапускает summarize (+ enrich);
  вручную перезапускать не нужно.

## Секция enrich (нужен compose-профиль `graph`)

```yaml
enrich:
  prompt: |              # обязательно; ОБЯЗАН содержать {transcript}
    Извлеки из транскрипта JSON: {"events": [...], "entities": [...],
    "relations": [...]} … {transcript}
  known_entities: true   # опционально; default false. true → top-25
                         # сущностей пространства в {known_entities};
                         # целое N → top-N. Включено → в промпте ОБЯЗАН
                         # быть плейсхолдер {known_entities}
  node_labels:           # опционально; defaults: Entity / Event
    entity: Entity
    event: Event
```

**`{known_entities}` (фаза 2)**: если `known_entities` включён, перед
извлечением хост читает top-N сущностей пространства ПЕРВОГО тега записи
(свои узлы записи исключены) и подставляет в промпт блок вида
`- slug — label (type)` (пустое пространство — литерал `(none)`); модель
переиспользует устоявшиеся slug'и вместо создания дублей. Снимок один
(из первого пространства), а не по одному на тег: извлечение — это ОДИН
LLM-вызов, покомпонентный пересчёт умножил бы стоимость на число тегов.
Событие в ответе модели может нести `"entities": ["slug", …]` —
объявленные упоминания: такие slug'и (только из множества извлечённых
сущностей) становятся рёбрами `MENTIONS` и полем `mentions` в
`meta/events.json`; без объявления работает прежняя эвристика «лейбл
встречается в summary».

После summarize хост просит LLM вернуть JSON-объект
`{events: [{ts, kind, summary}], entities: [{slug, label, type}],
relations: [{from_slug, to_slug, type}]}` и пишет его в Neo4j: узлы и рёбра
несут `tag` и `origin_recording_id`; повторный прогон идемпотентен
(DETACH DELETE по записи → MERGE по (tag, slug)); дедуп — slug-нормализация
+ LLM-вопрос «тот же объект?». Промпт подставляет ТОЛЬКО `{title}` и
`{transcript}` (литерально) — фигурные скобки JSON-примеров безопасны.
Типы сущностей и `kind` событий — английские системные имена, задаваемые
промптом профиля (см. «Язык системных имён»). Стадия best-effort: без
графа или enrich-секции — skipped, ошибка не портит запись.

## Устаревшее: `tags:`

Поле `tags:` (матч профиля по пересечению тегов записи) удалено из
контракта: файл с `tags:` логируется (warn) и пропускается как невалидный —
замените на `type:`. Маршрутизация конвейера теперь по типу записи; теги
записей остались пользовательской группировкой (память/дайджест живут в
пространстве тегов) и на выбор профиля не влияют.

## Будущие секции (forward-compat)

`digest:` (волна C) — неизвестные поля сегодня дают warn и игнорируются;
файлы с ними не ломают хост.
